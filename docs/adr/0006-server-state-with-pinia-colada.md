# 服务端数据交给 Pinia Colada，写接口与到达顺序无关，阅读进度独立成资源

前端原来为时序手写了一整套机制：`createRequest`（只认最后一次、响应落地时补上本地改动）、「本站账号数据只读一次、本地为准、整份 PUT 排队提交」、详情 store 的新鲜期与 `revision`、读阅读历史和详情前先等进度保存落地、各页面在 `onActivated` 里自己决定重读并各自防首次挂载多读一次。每种数据一套策略，改一处行为就冒出新的时序洞。根子有三个：服务端数据的缓存与作废是手写的、散在各处；写接口是整份快照，乱序就旧盖新，只好排队、只读一次、放弃跨设备同步；阅读进度是图集详情的一个字段，高频写、写后即读的数据和低频的上游元数据共用一份，每条写规则都要反过来修补读规则。

所以：前端的服务端数据统一交给 Pinia Colada（Pinia 官方的数据获取库，已经在用 Pinia，不另起一套状态容器；比 TanStack Vue Query 用的人少，这是取舍），按 query key 缓存，作废、去重、取消、乐观更新都用它的词汇；写接口改成与到达顺序无关——偏好按字段 `PATCH`，搜索历史改成「记一个词 / 删一个词 / 清空」，排序、去重、截断由服务端做；阅读进度从详情里拆出来成为独立资源，详情接口不再带进度。

## Consequences

- 偏好与搜索历史的写入仍然依次发出（同一字段的两次 `PATCH`、先记后删同一个词，乱序都会得到错的结果）；进度上报与删除阅读历史不排队。读本站账号数据之前一律先等已经发出的写入落地，不分是哪一类：只开一路，多等的也就是一次写入的时间，换来不必判断某份数据该等哪一路。排队与等待集中在 `shared/api/writes.ts`，「本地当场改、随后提交、失败重读」集中在 `shared/api/optimistic.ts`，各数据不再各写一套。
- 进度上报的合并窗口、页面收起与卸载时补发、`keepalive`、上报方加序号照旧：这是页面卸载的语义，查询库不管。
- Pinia Colada 不处理 KeepAlive：被留着的页面回来时不会重新挂载。只缓存需要保留界面状态的页面（搜索与阅读历史保留滚动与已翻的页，设置页保留没提交的草稿，节假日保留选中的日期），其中要「每次回来都重读」的在 `onActivated` 里 `refresh()`，在读时它复用那次请求，首次挂载不用另外防重。
- 换本站账号时清空整个查询缓存并丢掉还在排队的写入；换绑 e 站账号时按 `['eh']` 作废，搜索结果与阅读历史只留第一页重读，不把翻过的每一页都向上游重抓一遍。
